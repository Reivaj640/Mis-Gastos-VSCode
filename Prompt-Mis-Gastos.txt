## 11. ALCANCE Y RESPONSABILIDADES POR CAPA



**Mis-Gastos** es una PWA + aplicación de escritorio (Electron) **viva**,
de un solo usuario, con datos 100% locales y encriptados. Tiene
arquitectura existente, contratos de almacenamiento activos, tipado
estricto y un sistema visual oficial.



Toda solución debe:
- Respetar la arquitectura existente
- Preservar privacidad y seguridad por diseño (local-first)
- Mantener coherencia UX/UI con el sistema visual oficial
- Evitar efectos colaterales en estado persistido
- Respetar los esquemas encriptados del usuario
- Mantener retrocompatibilidad de respaldos JSON
- Priorizar mantenibilidad, accesibilidad (A11y) y trazabilidad



| Capa | Hace | NO hace |
|------|------|---------|
| **Renderer (Next.js / React)** | Renderiza, aplica tema, gestiona interacción y estado visual, dispara cálculos derivados | Persiste fuera de la abstracción de storage, recalcula reglas críticas en varios lugares, asume datos corruptos |
| **Servicios (`src/services/`)** | Lógica de negocio pura, cálculos de estado/categorías/períodos, formateo monetario, exportación CSV/JSON | Renderizar UI, tocar el DOM, acceder a localStorage directo |
| **Storage (Zustand persist + localStorage encriptado)** | Persistir, hidratar, restaurar desde backup, versionar esquema | Transformar reglas de negocio, mutar objetos compartidos |
| **Electron Main/Preload** | Empaquetado, auto-update, IPC mínimo (versión + updater), servir `out/` estático | Acceder a datos del usuario, romper el aislamiento del renderer |



### Stack tecnológico verificado



| Capa | Tecnología |
|------|-----------|
| Framework | Next.js 16 (App Router, Turbopack) |
| UI | React 19 + TypeScript 5 |
| Estilos | TailwindCSS v4 + tokens en OKLCH |
| Componentes | Shadcn/ui (variante `new-york`) + Radix UI |
| Estado | Zustand (`src/store/`) + `useLocalStorage` (uso activo) |
| Animación | Framer Motion |
| Iconos | Lucide React (**exclusivo**) |
| Datos | localStorage encriptado (Web Crypto API, AES-GCM) |
| Escritorio | Electron 41 + electron-builder (NSIS + Portable) |
| Actualización | electron-updater (auto-update desde GitHub Releases) |

> **Nota:** `src/store/useAppStore.ts` (Zustand) existe pero **no está en uso
> activo**. Las vistas leen y escriben mediante `useLocalStorage` desde
> `src/app/page.tsx`. No introduzcas Zustand como si ya gobernara el estado
> sin verificar antes.

**PROHIBIDO** inventar layouts arbitrarios. Toda vista usa UNO de estos patrones:

**Reglas:** densidad visual uniforme, scroll horizontal seguro en móvil, paginación solo si supera umbrales prácticos.

## 16. ARQUITECTURA TÉCNICA



### 16.1 Estado



- **Visual** pertenece al Renderer (React state, `useState`, `useMemo`)
- **Persistente** pertenece al storage (`useLocalStorage` o `useAppStore`)
- El storage **NO** controla estados visuales efímeros
- Los componentes **NO** persisten fuera de la abstracción



**PROHIBIDO:** duplicar estado, recalcular datos ya procesados en cada render, mutar objetos compartidos, mezclar estado UI con reglas de negocio.



**Flujo obligatorio:** UI → Acción → servicio puro (validación/cálculo) → setter de storage → re-render.



**Toda actualización debe:** minimizar re-renderizados, evitar listeners duplicados, limpiar efectos al desmontar, evitar memory leaks y race conditions (especialmente en el arranque de `page.tsx`, que lee localStorage directo para evitar problemas de hidratación).



**Toda operación async debe:** manejar loading, error, timeout y rollback seguro. Importante en el auto-updater de Electron (`UpdateManager`).



### 16.2 IPC Electron (MÍNIMO)



- `contextBridge` obligatorio en `electron/preload.js`
- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: false`
- `electronAPI` expuesto vía `contextBridge.exposeInMainWorld`



**Contratos actuales (NO ampliar sin versionar):**

| Método | Propósito |
|--------|-----------|
| `electronAPI.isElectron` | Indica si corre en escritorio |
| `electronAPI.getAppVersion()` | Versión instalada |
| `electronAPI.checkForUpdates()` | Busca actualizaciones |
| `electronAPI.installUpdate()` | Aplica la actualización |
| `electronAPI.onUpdateAvailable(cb)` | Evento: hay versión nueva |
| `electronAPI.onDownloadProgress(cb)` | Evento: progreso de descarga |
| `electronAPI.onUpdateDownloaded(cb)` | Evento: descarga completa |
| `electronAPI.onUpdateError(cb)` | Evento: error en la actualización |
| `electronAPI.onChecking(cb)` | Evento: revisando |
| `electronAPI.onNoUpdate(cb)` | Evento: ya está al día |



**PROHIBIDO:** exponer `ipcRenderer` directamente, usar `eval` o `executeJavaScript`, exponer APIs que toquen localStorage del renderer o datos del usuario, agregar canales IPC nuevos sin documentar.



**Naming de canales:** `modulo:accion` (ej. `update:check`).

### 16.3 Servicios (`src/services/`)



| Servicio | Responsabilidad |
|----------|-----------------|
| `expenseService.ts` | Lógica de negocio de gastos (estado, fechas de vencimiento) |
| `paymentService.ts` | Registro y validación de pagos |
| `loggerService.ts` | Logging estructurado (singleton `logger` + helper `log`) |



**Reglas:**
- Servicios exportan **funciones puras** u objetos con métodos puros.
- **NO** renderizan UI, **NO** tocan el DOM, **NO** acceden a localStorage.
- Toda regla de negocio vive en el servicio, no en el componente.
- Los componentes consumen servicios; nunca copian la lógica.



**Antes de crear un servicio nuevo:**
1. Verificar si existe equivalente en `expenseService` o `paymentService`.
2. Evaluar extenderlo de forma segura.
3. Mantener la firma tipada consistente.



### 16.4 Hooks (`src/hooks/`)



| Hook | Responsabilidad |
|------|-----------------|
| `useLocalStorage.ts` | Wrapper tipado para localStorage (preferente para estado de componente) |
| `use-toast.ts` | Sistema de notificaciones |
| `use-mobile.ts` | Detección de viewport móvil |



**Reglas:** responsabilidad única, sin lógica de negocio (eso va a servicios), y cleanup obligatorio en `useEffect` (timers y listeners).



### 16.5 Componentes (`src/components/`)



- **Reutilizar antes de crear** (Shadcn/ui + composición local).
- **Extender antes de duplicar** (variantes con `class-variance-authority` si aplica).
- Composición sobre sobreescritura.



**Antes de crear un componente nuevo:**
1. Verificar si existe equivalente en `src/components/ui/` (Shadcn) o en los managers existentes.
2. Evaluar extensión segura (slots, props, variantes).
3. Mantener la API visual consistente.



**Todo componente debe:** naming `PascalCase`, CSS solo con utilities y tokens, props tipadas, y estados claros (loading / empty / success / error / validation).

### 16.6 Performance y escalabilidad



**OBLIGATORIO:**
- `useMemo` para cálculos derivados pesados (KPIs del Dashboard, filtros de búsqueda)
- `useCallback` para handlers pasados a componentes memoizados
- Debounce en búsquedas (`AdvancedSearch`)
- Lazy loading cuando aplique (`next/dynamic` para vistas pesadas)
- **Virtualización en listas grandes** con `@tanstack/react-virtual` (sobre todo `PaymentHistory`)
- Limpieza de eventos y timers



**Considerar:** uso prolongado en el navegador, datasets grandes (>1000 pagos), consumo de RAM en Electron.



**PROHIBIDO:** re-renderizados innecesarios, listeners múltiples, recorridos del array completo en cada render, animaciones costosas en listas largas, `console.log` en producción (usar el logger).



### 16.7 Migraciones de esquema



- Incrementales, con fallback seguro.
- **Validar el esquema al leer**, tanto de localStorage como de un backup importado.
- Compatibilidad hacia atrás (respaldos antiguos deben seguir importándose).
- **PROHIBIDO** borrar campos existentes de `Expense`, `Payment`, `Income`, `AppSettings`.
- Los campos nuevos deben ser **opcionales** con valor por defecto seguro.
- Versionar el esquema en el backup JSON.



### 16.8 Seguridad (CRÍTICO EN MIS-GASTOS)



- **Sanitización XSS obligatoria** en TODO input del usuario: usar `sanitizeInput()` de `src/lib/security.ts`.
- **Escape CSV obligatorio** en exportaciones (`escapeCSV()` previene inyección de fórmulas).
- **Validación de integridad** con `generateDataHash()` y `validateDataIntegrity()`.
- **Encriptación AES-GCM** vía Web Crypto API.
- Principio de mínimo acceso: los servicios solo leen lo que necesitan.
- **PROHIBIDO:** interpolación insegura, `dangerouslySetInnerHTML` sin sanitizar, `eval`, `Function()`, almacenamiento inseguro de claves, exposición de rutas internas del sistema de archivos.
- **PROHIBIDO** enviar datos del usuario a cualquier servicio externo (sin servidor = sin telemetría).

## 17. CONTRATOS DE DATOS (INQUEBRANTABLES)



### 17.1 Tipos del dominio (`src/lib/types.ts`)



```ts
interface Expense {
  id: string;              // crypto.randomUUID() o fallback
  name: string;
  category: string;        // valor de CATEGORIES o "custom_<slug>"
  customCategory?: string;
  amount: number;
  dueDay?: number;         // 1-31
  isActive: boolean;
  createdAt: string;       // ISO
}

interface Payment {
  id: string;
  expenseId: string;
  amount: number;
  paymentDate: string;     // ISO
  period: string;          // "YYYY-MM"
  notes?: string;
  payerId?: string;
}

interface Income {
  id: string;
  name: string;
  amount: number;
  description?: string;
  color: string;           // valor de INCOME_COLORS
  isActive: boolean;
  createdAt: string;
}

interface AppSettings {
  currencySymbol: string;
  alertDays: number;       // por defecto 3
  customCategories: string[];
}
```



**PROHIBIDO sin versionar:** cambiar la estructura de retorno de los servicios, renombrar campos, cambiar tipos, eliminar datos al migrar, o cambiar el formato de `period` ("YYYY-MM").



**Si se requiere un cambio:** versionar el esquema en el backup y crear una rama de migración.



### 17.2 Storage (localStorage encriptado)



**Claves oficiales:**

| Clave | Contenido |
|-------|-----------|
| `expenses` | `Expense[]` |
| `payments` | `Payment[]` |
| `incomes` | `Income[]` |
| `appSettings` | `AppSettings` |
| `overdueToastShown` | `"true"` (en sessionStorage, es una flag de UI) |



**Toda lectura/escritura pasa por** `useLocalStorage<T>(key, defaultValue)`,
o por `useAppStore` si se requiere historial de deshacer/rehacer.
(Nota: hoy `useAppStore` existe pero no está en uso activo; las vistas
usan `useLocalStorage` directamente en `page.tsx`.)



**PROHIBIDO:** acceder a `localStorage` fuera de `useLocalStorage` o de
`page.tsx`. Excepción ya documentada: el `useEffect` de arranque en
`page.tsx` lee localStorage directamente para evitar problemas de hidratación.



### 17.3 Backup JSON



**Formato:**

```json
{
  "version": "2.1.3",
  "exportedAt": "2026-10-02T...",
  "data": {
    "expenses": [],
    "payments": [],
    "incomes": [],
    "settings": {}
  }
}
```



**Reglas:**
- El import debe sanitizar, verificar versión y migrar si hace falta.
- Si el JSON es de una versión más nueva → rechazarlo con mensaje claro.
- Si no tiene `version` → tratarlo como legacy e intentar mapear campos.
- NUNCA sobrescribir sin confirmación del usuario.



### 17.4 Formato de respuesta de servicios



```ts
// Para operaciones que pueden fallar (import, update, etc.)
{
  success: boolean,
  data?: T,
  error?: { code: string, message: string }
}
```



Para cálculos puros (`getExpenseStatus`, `formatCurrency`, `getCurrentPeriod`)
→ retorno directo del valor.

### 18.1 Logging estructurado



**Formato:** `[MIS-GASTOS][MÓDULO][ACCIÓN][ESTADO]`



**Ejemplo:** `[MIS-GASTOS][PAYMENT][SAVE][SUCCESS]`



Usar siempre vía `import { logger } from "@/services/loggerService"` o `log.info()`.



**Niveles:** `debug`, `info`, `warn`, `error`. El logger es singleton, con un máximo de 1000 entradas en memoria y descarga como `app-logs.json`.



**PROHIBIDO:** `console.log` sueltos en producción, logs ambiguos, errores silenciosos, o exponer trazas internas al usuario final.



### 18.2 Estados UX obligatorios



Toda vista debe soportar: **loading, empty, success, error, offline** (cuando aplique).



| Estado | Componente canónico |
|--------|---------------------|
| Loading | `Skeleton` (Shadcn) o spinner con ícono `Wallet` |
| Empty | `EmptyState` (`src/components/EmptyState.tsx`) |
| Error | `AlertDialog` o mensaje inline con acción de reintento |
| Success | `toast` de Sonner |
| Offline | No aplica (PWA + Electron funcionan sin red por diseño) |



**PROHIBIDO:** pantallas vacías sin contexto, loaders infinitos, errores genéricos ("Algo salió mal"), o bloqueos silenciosos.

## 20. PRIVACIDAD Y ENCRIPTACIÓN (SECCIÓN CRÍTICA)



> ⚠️ Esta sección es **INQUEBRANTABLE**. Mis-Gastos es **local-first por diseño**.



**Principios:**
1. **Cero servidor**: ningún dato del usuario sale del dispositivo.
2. **Encriptación AES-GCM** vía Web Crypto API (nativa del navegador / Chromium de Electron).
3. **LocalStorage encriptado**, no plano.
4. **Sanitización XSS** en todo input (`sanitizeInput`).
5. **Validación de integridad** al importar respaldos.
6. **Sin telemetría**: `loggerService.sendToMonitoring()` es un placeholder — **NO** implementar envío real sin consentimiento explícito del usuario.



**PROHIBIDO:**
- Enviar datos a endpoints externos.
- Agregar analytics, tracking, píxeles o beacons.
- Persistir claves de encriptación en lugares inseguros.
- Mostrar información sensible en logs visibles al usuario.
- Agregar servicios cloud (Firebase, Supabase, etc.).



**Respaldos (exportar/importar JSON):**
- El usuario es responsable de guardar el archivo `.json` en un lugar seguro.
- Documentar siempre que si borra el caché del navegador sin backup, **pierde los datos**.
- El import debe pedir confirmación antes de sobrescribir.
